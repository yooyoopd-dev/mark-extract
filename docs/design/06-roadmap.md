## 1. 프로젝트 골격 + 디자인 토큰 ✅ 완료

Electron 프로젝트 초기화, 3계층 분리, `design/index.html`에서 토큰 추출 (`styles/tokens.css`).

**검증 결과** — `npm run verify` 하나로 돌아간다.

| 기준 | 결과 |
|---|---|
| 빈 셸이 뜨고 라이트/다크 전환이 동작한다 | 통과. xvfb에서 창을 띄워 두 테마 스크린샷 확보 |
| `tokens.css`의 색 45쌍이 `design/index.html`과 일치한다 | 통과. 90개 토큰 일치. 파일 대조(`tokens:check`)와 실행 중 계산값 대조(스모크) 두 층 |
| `nodeIntegration: false` / `contextIsolation: true` / `sandbox: true` | 통과. 소스 grep이 아니라 실행 중 `webContents.getLastWebPreferences()`에서 확인 |

**정한 것**

- 번들러를 쓰지 않는다. 렌더러가 프레임워크 없는 순수 HTML/CSS/JS라 번들할 대상이 없다. `tsc`만 쓰고 의존성은 `electron`·`electron-builder`·`typescript`·`@types/node` 넷뿐이다. (`electron-vite@5`의 peer는 `vite ^5|^6|^7`인데 현재 vite는 8.x라 맞지도 않는다.)
- 색 토큰은 `scripts/tokens.mjs`가 `design/index.html`에서 생성한다. `tokens.css`는 커밋하되 `tokens:check`가 드리프트를 잡고, 어긋나면 **빌드가 실패한다**. 손으로 옮기다 한 글자 틀리는 경로를 없앴다.
- 반지름·타이포·모션은 원본에 CSS 변수가 아니라 리터럴로 있어 생성 대상이 아니다. `base.css`에 손으로 올리되 값은 원본 그대로 뒀다.

**실측으로 정정한 것**

- Electron의 `file://`은 `<script type="module">`을 **정상적으로 싣는다.** 설계 당시 일반 브라우저처럼 CORS로 막힐 것이라 적었으나 실제로는 로드된다. 4단계에서 커스텀 프로토콜을 들일 필요가 없다.
- TypeScript 7에서 `moduleResolution: node10`과 `module: none`이 제거되었다. 각각 기본값과 `ESNext`로 바꿨다.

**미검증**: `electron-builder.yml`은 `05-packaging.md` 명세대로 작성만 했다. 리눅스 컨테이너에서 Windows portable 빌드를 돌릴 수 없어 8단계에서 확인한다.

## 2. PDF 어댑터 + JRE 동봉

`jdeps`로 모듈 결정 → `jlink` 스크립트 → PDF 어댑터 → 헬스 체크(`--export-options`).

**검증 결과** — `npm run verify:pdf` 가 단언 15개를 돌린다.

| 기준 | 결과 |
|---|---|
| 제목 계층과 표가 살아남는다 | 통과. H1·H2·H3, 표 헤더·구분행·내용 |
| 한글이 깨지지 않는다 | 통과. UTF-8, 숫자·특수문자·따옴표 보존 |
| 임시 디렉터리가 지워진다 | 통과. 성공·실패·취소 모두 `finally` 에서 |
| 동봉 JRE 를 쓴다 | 통과. 개발 경로와 **패키징 경로(`process.resourcesPath`) 모두** |
| Java 미설치 Windows | **CI 가 확인** — `debug-windows` job |

**정한 것**

- JAR 은 `@opendataloader/pdf` 를 devDependency 로 두고 빌드 때 `resources/lib/` 로 꺼낸다. 24MB 바이너리를 git 에 넣지 않으면서 `package-lock` 으로 버전을 고정한다. npm 래퍼 자체는 런타임에 쓰지 않는다 — 그건 PATH 의 `java` 를 찾는데 우리는 동봉 JRE 를 쓴다.
- 결과는 stdout 이 아니라 파일로 받는다. `--to-stdout` 이 있지만 Windows 콘솔 코드페이지의 영향을 받을 여지가 있다.
- 공유 타입(`ParseResult` 등)은 `src/shared/*.d.ts` 로 뒀다. 타입 선언뿐이라 main·preload·renderer 가 모두 쓰면서 어느 쪽에서도 JS 가 나오지 않는다.
- 앱에 `--self-test` 를 넣었다. 패키징된 뒤에야 `process.resourcesPath` 경로가 검증되고, 사용자도 GUI 없이 명령 프롬프트에서 바로 확인할 수 있다.

**실측으로 드러난 결함과 대응**

1. **한글 줄 잇기** — 기본 출력이 `섞여 있 으며` 처럼 단어 가운데 공백을 넣는다. PDF 줄바꿈에서 문단을 이을 때 공백을 넣는 동작이 한글에선 틀리다. `--keep-line-breaks` 로 받아 CJK 를 보며 직접 잇도록 했다 (→ [02](02-parser-adapters.md#한글-줄-잇기--2단계-실측-이-단계의-핵심))
2. **`--space-ratio` 는 올리면 안 된다** — 0.30 에서 정당한 공백까지 사라지고 원래 문제는 그대로다. UI 에 내보내지 않는다
3. **목록 마커 소실** — 불릿이 `-` 없는 문단으로 풀린다. 엔진 한계이며 알려진 제약으로 문서화했다

**실측치**: jlink JRE **54MB**(추정 45MB 였음), JAR 23.1MB, 변환 0.5초/1페이지.

**Windows 확인 경로**: `.github/workflows/build.yml` 의 `debug-windows` job 이 Windows JRE 로 변환을 검증하고 portable exe 를 아티팩트로 올린다. 사용자가 내려받아 `MarkExtract.exe --self-test` 또는 GUI 에 PDF 를 떨어뜨려 확인한다.

## 3. Office · PPTX 어댑터 ✅ 완료

kordoc 연결(`--omit=optional`), PPTX 자체 구현.

**검증 결과** — `npm run verify:parsers` 가 단언 **52개**를 돌린다.

| 기준 | 결과 |
|---|---|
| DOCX/XLSX/XLS/PPTX 가 표·제목 계층을 유지한다 | 통과 |
| PPTX 에 슬라이드 경계·발표자 노트·표가 나온다 | 통과 |
| kordoc 오류 코드가 UI 문구로 매핑된다 | 통과 (`ErrorCode` → 문구·버튼 표) |
| 매직 바이트 판별이 확장자가 틀려도 맞는다 | 통과 (`.pdf` 로 이름 붙인 docx → docx) |
| 패키징된 앱에서 다섯 형식이 모두 변환된다 | 통과 (5/5, `--self-test`) |

**실측으로 드러난 것**

1. **줄 잇기를 PDF 전용으로 분리했다.** 스프레드시트에서 연속한 두 줄은 서로 다른 셀이라, PDF 용 줄 잇기를 적용하면 별개 값이 한 줄로 뭉개진다. `normalizeMarkdown`(공통)과 `joinWrappedLines`(PDF 전용)를 나눴다
2. **`.npmrc` 의 `omit=optional` 은 쓸 수 없다.** TypeScript 7 의 플랫폼 바이너리가 optionalDependencies 라 tsc 가 깨진다. 대신 패키징 단계에서 걸러내 **asar 75MB → 25MB**
3. **PPTX 제목이 내용 뒤로 밀렸다.** 자리표시자가 `a:off` 를 생략하고 레이아웃에서 위치를 물려받는데 XML 만 읽는 우리는 알 수 없다. 제목을 위치와 무관하게 맨 앞으로 보낸다
4. **PPTX 도형은 `p:spTree` 직계 자식만** 본다. `getElementsByTagNameNS` 는 모든 자손을 훑어 그룹 안 도형이 중복된다

**알려진 제약**: 목록 마커가 사라지는 것은 PDF 뿐 아니라 **DOCX 도 마찬가지**다. 불릿이 `-` 없는 문단으로 풀린다.

## 4. UI 이식 ✅ 완료

사이드바·목록·뷰어·인스펙터·상태바·팔레트·다이얼로그·토스트.

**검증 결과** — 스모크가 실제로 띄운 창에서 확인한다.

| 기준 | 결과 |
|---|---|
| 1024/1366/1440/1920 에서 가로 스크롤 없음 | 통과. 각 폭 스크린샷 확보 |
| 1200px·1024px 에서 드로어 전환 | 통과. `position: absolute` 전환을 계산값으로 확인 |
| 키보드로 목록 이동·탭 전환 | 목록 ↑↓, 탭 ←→, Esc 로 드로어 닫기, Ctrl+K 팔레트 |
| 문서 상태 4종의 색이 토큰과 일치 | 통과 (색 토큰 45쌍 대조에 포함) |
| UI 를 통한 실제 변환 | 통과. 시험 자료 4종이 목록에 '완료'로 들어옴 |

**정한 것**

- **프레임 없는 창**(`frame: false`)으로 바꿨다. 디자인이 Windows 캡션바를 직접 그리므로 기본 프레임을 쓰면 캡션이 둘이 된다. 최소화·최대화·닫기는 `window:action` 채널 하나로 처리하되 main 이 값을 검사한다. 타이틀바에 `-webkit-app-region: drag` 를 준다
- **명령줄 인자로 문서를 연다.** `MarkExtract.exe 보고서.pdf` — 탐색기의 "연결 프로그램"에 해당한다. 덕분에 스모크가 테스트 전용 훅 없이 채워진 UI 를 검증할 수 있다
- **인라인 style 속성을 전부 클래스로 옮겼다.** CSP 를 `style-src 'self'` 로 잠갔기 때문에 원본의 `style="…"` 9곳이 차단됐다. `'unsafe-inline'` 을 여는 대신 값을 그대로 클래스로 옮겼다

**이식하며 드러난 것**

1. **1단계의 스크롤 버그는 원본에 이미 답이 있었다.** 원본의 `.workspace > * { min-width: 0; min-height: 0; }` 를 1단계에서 레이아웃을 직접 쓰며 빠뜨린 것이 원인이었다
2. **CSS 추출에 `<style>` 태그가 섞여 들어갔다.** 파서가 뒤따르는 `@layer od-layout` 블록을 통째로 버려 `.od-scroll { overflow-y: auto }` 가 죽었고 뷰어가 스크롤되지 않았다
3. **가로 스크롤 검사를 두 번 잘못 짰다.** `scrollWidth` 는 닫힌 드로어(`translateX(102%)`)까지 세고, `overflow: hidden` 은 프로그램적 스크롤을 막지 않으며, 루트의 computed overflow 는 뷰포트로 전파된 값이 아니다. 결국 **body 의 overflow 기전**과 **드로어를 뺀 요소의 화면 이탈** 둘로 나눠 본다

**디자인 대비 변경 (문서대로)**: 3번째 탭 '추출 필드' → '변환 로그', 인스펙터에 엔진 선택 추가·청크 슬라이더 제거·OCR 조건부 비활성.

**아직 없는 것**: LLM 엔진(6단계), OCR(7단계). 해당 버튼은 비활성이거나 안내 토스트를 띄운다.

## 5. 변환 큐 · 감시 폴더 · 내보내기 — 완료

**검증** (`npm run verify:queue`, 40개 단언)

| 기준 | 어떻게 확인했나 |
|---|---|
| 폴더를 드롭하면 지원 포맷만 큐에 들어간다 | 하위 폴더까지 훑고 `.txt`·`.hwp`·숨김 파일을 거른다 |
| 취소가 자식 프로세스를 실제로 죽인다 | `ps` 로 자바가 뜬 것을 본 뒤 취소하고 250ms 안에 사라지는지 본다 |
| 재변환이 바뀐 옵션을 반영한다 | 어댑터 명령줄(변환 로그의 `인자`)에 플래그가 실렸는지 본다 |
| 한 문서가 실패해도 큐가 계속 진행된다 | 깨진 PDF 를 앞에 두고 뒤의 두 건이 완료되는지 본다 |
| 내보낸 파일이 BOM 없는 UTF-8이다 | 바이트를 직접 읽어 BOM 부재와 한글 보존을 확인한다 |

감시 폴더도 같은 스크립트에서 본다: 걸 때 이미 있던 문서, 뒤에 떨어진 문서,
지원하지 않는 형식 무시, 해제 뒤 유입 중단.

**정한 것**

- **문서는 main 이 들고, 렌더러는 그린다.** 감시 폴더가 붙는 순간 문서가 늘어나는
  경로가 둘이 되므로(사용자 · 파일 시스템) 소유자가 하나여야 한다. 렌더러는
  `doc:changed` 스냅샷을 받아 그리고, 동작은 IPC 로 부탁한다
- **마크다운 본문은 스냅샷에 싣지 않는다.** 문서당 수백 KB 이고 큐는 최대 1000건이다.
  선택한 문서 것만 `doc:markdown` 으로 따로 받는다. 대신 목록 검색은 파일명과
  미리보기까지만 본다
- **동시 실행 기본 1.** JVM 콜드 스타트가 문서당 수 초라 병렬 이득이 작고, 자바
  프로세스 여러 개가 동시에 메모리를 먹는 쪽이 더 위험하다. 설정에서 4까지
- **덮어쓰지 않는다.** 같은 이름이 있으면 `-1`, `-2` 를 붙인다
- **시제품의 JSONL 선택지를 뺐다.** 출력은 Markdown 전용이다(결정 3). 내보내기
  다이얼로그의 "이미지 참조" 항목도 뺐다 — 그것은 변환 옵션이라 인스펙터에 있고,
  이미 변환된 결과를 내보낼 때 바꿀 수 있는 것이 아니다

**검사를 짜며 드러난 것**

1. **`ps` 를 `args` 로만 걸러 자바 프로세스를 셌더니 거짓 통과·거짓 실패가 났다.**
   명령줄에 JAR 이름이 스쳐 지나가는 셸까지 잡힌다. 실행 파일 이름이 `java` 인
   것만 센다
2. **취소 검사를 1.5초 뒤에 하면 아무것도 확인하지 못한다.** 이 시험 자료는 1초
   안팎이면 변환이 끝나 자연히 끝난 것과 죽인 것이 구별되지 않는다. SIGKILL 을
   빈 함수로 바꿔 보니 그제서야 드러났다
3. **`--include-header-footer` 로 결과가 달라지는지 보려 했으나 시험 자료에
   머리글·바닥글이 없어 출력이 같았다.** CLI 로 직접 확인한 뒤, 결과 대조 대신
   어댑터 명령줄에 플래그가 실렸는지를 본다
4. **스모크에 `broadcastChanges()` 를 빠뜨려 큐가 진행돼도 화면이 갱신되지 않았다.**
   프로덕션 `main/index.ts` 와 초기화가 어긋나면 이렇게 드러난다

**여기서부터 릴리스한다.** 검증 두 판이 모두 통과하면 프리릴리스로 게시한다
(`.github/workflows/build.yml` 의 `release` job). 아티팩트는 90일 뒤 사라지고
로그인해야 받을 수 있지만 릴리스는 남고 링크 하나로 받는다.

## 6a. LLM CLI 계층 — 완료

CLI 탐색, 프로바이더 4종 transport, 모드 A 격리, 오류 진단. 엔진 선택은 인스펙터에서 한다.

> **차용 기준 (결정 14)**: llm-co-wiki에서 가져오는 것은 CLI 인자 조합·프로토콜 사실·운영 사실뿐이다. **코드는 복사하지 않고 새로 쓴다.** 재작성 범위는 CLI transport 4종, 실행 파일 탐색기, 오류 진단. 이유와 허용 경계는 [ATTRIBUTION](ATTRIBUTION.md#llm-co-wiki-차용-기준-결정-14) 참조.

**검증** (`npm run verify:llm`, 단언 60개 + 실제 claude 실측)

| 기준 | 어떻게 확인했나 |
|---|---|
| 4개 프로바이더가 탐지되고, 없을 때 진단 리포트가 나온다 | 가짜 CLI를 PATH에 두고 탐색, 없는 PATH로 리포트 확인 |
| 모드 A: 임시 폴더에 대상 1개만 있고, 종료 후 지워진다 | 가짜 CLI가 `cwd`의 목록과 받은 인자를 본문에 실어 보낸다 |
| 모드 B: 프로바이더 4종 모두에서 변환 성공 | 가짜 CLI 4종 + 실제 claude |
| claude 스트림에서 텍스트 중복이 없다 | 증분만 / 전체만 / 섞임 / **뒤처진 assistant** 네 경우 |
| 인증 만료 시 전용 안내가 뜬다 | stderr에 인증 문구를 흘리는 가짜 CLI |
| 성공했는데 빈 결과면 실패로 처리된다 | 종료 코드 0 + 빈 본문 |

**정한 것**

- **모델 이름을 앱에 박지 않는다.** 자유 입력으로 두고 비우면 CLI 기본값을 쓴다. CLI 버전마다 받는 이름이 달라 목록을 고정하면 금방 낡는다. Ollama 드롭다운만 6b에서 `/api/tags`로 채운다
- **모드 A의 격리는 인자에 달려 있다.** 그래서 인자 조합 자체를 단언으로 잠가 두었다 — 실수로 `--allowedTools`가 빠지면 LLM이 볼 수 있는 범위가 넓어진다
- **`run.ts`는 `convert()`를 직접 부르지 않는다.** `convert.ts`가 `run.ts`를 부르므로 순환이 된다. 모드 B의 1단계를 호출자가 함수로 넘긴다
- **펜스 벗기기는 LLM 경로에만 둔다.** `normalizeMarkdown()`에 넣으면 본문에 정당하게 들어 있는 코드 블록까지 건드린다 (5단계에서 `joinWrappedLines`를 PDF 전용으로 떼어낸 것과 같은 이유)

**실측으로 드러난 것**

1. **`--input-format stream-json`을 쓰면 안 된다.** 설계 초안이 적어 둔 인자 조합대로 돌렸더니 `Error parsing streaming input line: SyntaxError`로 실패했다. 그 플래그를 켜면 stdin도 stream-json이어야 한다. `-p`는 평문 stdin을 그대로 프롬프트로 받는다
2. **모드 A에 `--permission-mode plan`을 쓰면 끝나지 않는다.** 승인을 기다린다. 사람이 앉아 있지 않으므로 `dontAsk`로 두고 대신 허용 도구를 읽기 전용으로 좁혔다
3. **평문을 흘리는 프로바이더(ollama)에서 줄바꿈이 사라졌다.** 실행기가 줄을 끊으며 개행을 떼어 내고 빈 줄을 건너뛰었다. JSON 프로바이더는 본문 안에 개행을 담아 오므로 드러나지 않던 결함이다
4. **"중복이 없다"를 부분 문자열 개수로 세면 중복을 놓친다.** 세던 문구가 본문 끝에 있어서, 누적 복사본이 여러 개 이어져도 완전한 형태로는 한 번만 나왔다. 전체를 통째로 비교하도록 바꾸고 나서야 결함 2건이 드러났다

**실측 항목 1 — 포맷 × 프로바이더**: claude만 쟀다. **PDF만 읽고 DOCX·XLSX·XLS·PPTX는 읽지 못한다.** 설계 초안이 DOCX를 "가능(알려짐)"으로 적어 둔 것은 틀렸다 — 그것은 API의 문서 첨부 기능이고, CLI가 읽기 도구만 가진 상태와는 다르다. gemini·codex는 설치하지 않아 "미검증"으로 남겼다.

이 실측이 결정 17을 실제로 쓰게 만들었다. 모드 A로 DOCX를 넣으면 claude가 "형식을 다루지 못한다"고 **산문으로** 답하는데, 그대로 두면 42자짜리 거절문이 변환 결과로 저장된다. 길이로 짐작하는 대신 프롬프트가 정확한 표식(`MARKEXTRACT_CANNOT_READ`)을 요구하게 하고 실행기가 그것만 본다.

**실측 항목 2 — `ollama run`**: **하지 못했다.** 개발 환경에서 `ollama.com`과 `registry.ollama.ai`가 네트워크 정책에 막혀 모델을 내려받을 수 없었다. 어댑터는 설계 문서의 서술(평문 스트림)을 가정해 구현했고 가짜 CLI로 우리 쪽 파싱만 검증했다. 가정 자체는 Ollama가 설치된 환경에서 확인해야 한다.

### 덤으로 드러난 것 — `--quiet`가 로그를 통째로 삼키고 있었다

서버가 꺼졌을 때 CLI는 설치·구동 안내까지 담은 친절한 `SEVERE`를 낸다. 그런데 2단계부터 고정으로 붙이던 `--quiet`가 `java.util.logging`을 통째로 꺼서 그것이 **한 글자도 나오지 않았다.** 실패는 `변환 엔진이 1 로 끝났습니다`만 남았다.

같은 이유로 **`collectWarnings()`는 처음부터 죽은 코드였다.** `WARNING: Detected background on page 1` 같은 실제 경고가 5단계 내내 조용히 버려지고 있었다. `--quiet`를 빼고 `javaLog()`로 레벨별로 가르니 경고가 되살아났다.

`spawn EINVAL`과 같은 종류의 문제다 — 실패가 화면에 도달하지 못하면 사내망에서는 손쓸 방법이 없다.

- **실제 OCR 인식 결과.** docling이 HuggingFace에서 모델을 받는데 개발 환경이 그것을 막는다. 서버까지 닿는 것과 실패를 읽는 것까지만 확인했다

## 8. 패키징 — 완료

### 배포하는 파일이 CI 에서 한 번도 실행된 적이 없었다

이 단계의 출발점은 워크플로를 다시 읽다 드러났다.

- `debug-windows` 의 자체 점검은 `dist/win-unpacked/*.exe` 를 돌렸다 — 압축을 **풀어 놓은** 디렉터리다
- `release` 가 사용자에게 주는 것은 `dist/*.exe` — `portable` 타깃의 **자기 압축 해제 단일 실행 파일**이다

둘은 다른 물건이고, 단일 exe 의 압축 해제·인자 전달·종료 코드는 아무도 확인하지 않고 있었다. 거기에 러너에는 `setup-java` 로 JDK 21 이 깔려 있어, 어댑터가 동봉 JRE 대신 시스템 `java` 로 새도 초록이 떴다.

**이제 `debug-windows` 가 배포하는 그 exe 를 `PATH` 에서 JDK 를 뺀 채 돌린다.** 두 점검을 모두 남긴 이유는 갈라 보기 위해서다 — `win-unpacked` 가 통과하고 단일 exe 가 실패하면 portable 스텁의 문제이고, 둘 다 실패하면 패키징 배치의 문제다.

**검증**

| 기준 | 결과 |
|---|---|
| 클린 Windows VM(Java·Node 없음)에서 단일 exe 가 실행된다 | **CI 로 흉내만 냈다** — `JAVA_HOME` 을 비우고 `PATH` 에서 JDK 를 뺀 Windows 러너. 자체 점검이 `동봉 JRE` 로 5종을 변환해야 통과한다. Java 가 설치된 적 없는 진짜 PC 확인은 사용자 몫 |
| 1~7단계 검증을 그 VM 에서 재실행해 통과한다 | **문자 그대로는 불가능** — 아래 |
| 첫 실행 지연에 스플래시·진행 표시가 나온다 | 통과. 구간을 셋으로 갈라 각각 덮었다 ([05](05-packaging.md#첫-실행)) |
| 실제 exe 크기를 재서 05 의 추정치를 실측치로 교체 | **264.8MB** (`useZip` 적용 뒤. 적용 전 173MB, 추정 110~130MB 였음). CI 가 매 빌드에서 찍는다 |

### "VM 에서 검증을 재실행"을 다시 잡았다

검증 스크립트 여섯 판은 Node·저장소·xvfb 가 있어야 돈다. 사내 PC 에 그것을 깔게 하는 것은 이 제품의 전제(단일 exe, 설치 없음)와 정반대다. 그래서 **패키징된 앱에서만 확인할 수 있는 것**으로 바꿔 `--self-test` 에 실었다. 전부 이미 있는 함수를 부른다.

- **LLM CLI 4종** — `resolveCli()` 로 찾고 `probeCli()` 로 실제로 띄운다. 찾음/실행됨/없음
- **hybrid OCR 서버** — `testHybrid(settings().hybridUrl)`
- **설정 경로** — `%APPDATA%` 에 실제로 써 보고 지운다. 막힌 PC 에서는 설정이 매번 기본값으로 돌아간다

종료 코드는 **변환 결과로만** 정한다. LLM CLI 와 OCR 서버는 사용자가 따로 깔고 띄우는 것이라 없는 것이 정상이고, 그것으로 패키징이 실패했다고 말하면 CI 가 언제나 빨갛다.

### 덤으로 드러난 것 — 탐지 제한 시간 5초가 모자랐다

`--self-test` 에 CLI 탐지를 실으니 그날 처음 띄운 gemini·codex 가 **둘 다 5초 안에 `--version` 에 답하지 못했다.** 두 번째부터는 각각 1.5초·0.05초다. 첫 실행이 느린 것은 CLI 도 마찬가지이고, 사내 PC 는 백신이 큰 JS 번들을 전수 검사하므로 더 느리다. 5초로는 **멀쩡히 도는 CLI 를 설정 화면이 "실행하지 못했습니다"로 적는다.** 15초로 올렸다.

`--quiet` 가 경고를 삼키던 것과 같은 종류다 — 화면에 뜨는 말이 틀리면 사내망에서는 손쓸 방법이 없다.

### 실측으로 드러난 것 — 매번 20초씩 푼다 (고쳤다)

단일 exe 의 `--self-test` 를 연달아 두 번 돌려 22.4초 · 21.4초(run 18), 23.9초 · 19.6초(run 19)를 얻었다. **두 번째가 빨라지지 않는다** — 압축 해제 결과를 재사용하지 않는다는 뜻이고, "첫 실행만 느리다"는 전제가 틀렸다.

처음에는 `portable.unpackDirName` 으로 캐시할 수 있으리라 적었는데 **그것도 틀렸다.** `portable.nsi` 가 `$INSTDIR` 를 앞뒤로 `RMDir /r` 하므로 어떤 이름을 주든 재사용은 없다. 그 옵션은 어디에 풀지만 바꾼다.

| | 1회차 (3회) | 2회차 (3회) |
|---|---|---|
| 기본 (7z) | 20.5 · 22.4 · 23.9초 | 17.5 · 19.6 · 21.4초 |
| **`useZip`** | 11.6 · 21.8 · 26.3초 | **9.4 · 12.7 · 12.8초** |

**1회차는 결론을 낼 수 없다** — `useZip` 표본이 7z 의 범위와 통째로 겹친다. 그 폭은 러너 편차다(문서만 바꾼 run 24 가 같은 exe 로 11.6초를 냈다). **2회차는 `useZip` 의 최악 표본이 7z 의 최선 표본보다 빠르다.** 맞바꿈은 exe 173MB → 264.8MB 이고, 근무 중 여러 번 띄우는 쪽이라 유지하기로 했다 ([05](05-packaging.md#첫-실행)).

여기서 배운 것 둘. **비교 대상은 같은 위치에서 재야 한다**(자리가 다르면 두 배 차이가 난다). 그리고 **표본 하나둘로 결론 내지 않는다** — 이 절의 숫자를 세 번 고쳐 쓰고서야 범위가 겹친다는 것을 봤다.

덤으로 압축 전 실제 크기가 **약 660MB** 라는 것도 드러났다 — 05 의 "약 280MB" 추정은 두 배 넘게 빗나갔다.

같은 실측에서 **단일 exe 의 stdout 이 호출자에게 닿지 않는 것**도 드러났다. NSIS 스텁이 한 겹 끼어 있어 종료 코드 0 은 돌아오는데 리다이렉트한 파일이 비어 있었다. `--self-test-out <파일>` 을 두어 같은 내용을 파일로도 남긴다.

### 고치지 않은 것

- **패키징된 Windows 앱의 구간 2**(창이 뜨기까지)를 재지 못했다. 창이 뜬 시점을 프로세스 밖에서 알 방법이 없다
- 7단계에서 남은 것들 — 실제 OCR 인식, gemini·codex 성공 응답 본문, Ollama 실동작, 암호 입력란

## build.8 실측 반영

사용자가 [v0.1.0-build.8](https://github.com/yooyoopd-dev/mark-extract/releases/tag/v0.1.0-build.8)을
Windows에서 직접 돌려 4건을 보고했다. Claude Code는 정상이었고 나머지 셋이 결함이었다.

| 보고 | 원인 | 조치 |
|---|---|---|
| DOCX 표가 `<table><tr><th>`로 | kordoc이 병합 셀에서 HTML로 빠진다 | `html-in-markdown.ts`가 파이프 표로. 병합은 펼치고 경고 |
| PDF에 `<br>` `&lt;br&gt;` | opendataloader가 표 안에서 `<br>`를 내고 `<` `>` `&`를 이스케이프한다 | 엔티티 디코드 + 렌더러가 `<br>`만 허용 목록으로 되살림 |
| Ollama가 끝나지 않음 | 진행 표시가 없어 느린 것과 멈춘 것을 구별할 수 없음 | 상태 칩·진행률 바 복원, 경과 시간·글자 수, LLM 30분 |

### 왜 우리 검증이 놓쳤나

**시험 자료가 단순해서다.** `sample-ko.*`의 표는 3×3이고 병합도 셀 안 줄바꿈도 없다.
단언 52개가 전부 통과하는데도 실제 문서에서 깨졌다. 단언을 일부러 깨뜨려 확인하는
습관은 5·6a에서 거짓 통과 4건을 잡았지만, **자료에 없는 것은 그 습관으로도 잡히지
않는다.**

그래서 `sample-table.docx`/`.pdf`를 더했다. 만들면서 같은 함정을 한 번 더 밟았다 —
처음에는 특수문자를 표 안에만 뒀는데, 엔티티 디코드를 통째로 없애도 검증이 통과했다.
xmldom이 표를 파싱하며 엔티티를 풀어 주기 때문이다. **표 밖에도 특수문자를 둬야**
디코드 경로가 실제로 검증된다.

### 덤으로 드러난 회귀

4단계 이식에서 상태 칩 클래스를 `.status`가 아니라 `.st`로 옮겨 적었다. `.st`는 어느
CSS에도 없어 칩에 배경색이 없고 스피너도 돌지 않았다. **색 토큰 45쌍을 대조하는
검사로는 이것이 잡히지 않는다** — 토큰 값은 맞고 규칙이 안 걸린 것이기 때문이다.
스모크가 이제 계산된 스타일로 본다.

### 고치지 않은 것

- **kordoc이 표 셀의 공백을 지운다** (`sanitizeText` 휴리스틱). 끄는 옵션도, 복원할
  방법도 없다. 문서에 기록만 남겼다
- **Ollama가 끝나지 않는 원인**. 재현할 수 없어 단정하지 않는다

## build.10 실측 반영 — Windows에서 `.cmd` CLI를 실행하지 못했다

사용자가 Windows에서 Gemini CLI로 변환하자 **`spawn EINVAL`**로 즉시 실패했다.

### 원인 넷

1. **Node가 `.cmd` 직접 실행을 막는다.** CVE-2024-27980 이후 `shell` 없이 배치 파일을 spawn하면 `EINVAL`이다. gemini·codex는 npm 셰임(`*.cmd`)뿐이라 어느 쪽으로도 돌 수 없었다
2. **우리가 셰임을 일부러 먼저 골랐다.** 후보 순서가 `.cmd` → `.exe`였다
3. **탐지가 실행을 해 보지 않았다.** 파일이 있는지만 봐서, 설정 화면은 "찾음"이라 말하고 변환은 죽었다
4. **리눅스 CI가 이 경로를 밟지 않는다.** 가짜 CLI 셰임을 `#!/bin/sh`로 만들었고, Windows job은 파서 검증만 돌렸다 — **LLM 계층은 Windows에서 한 번도 돌아 본 적이 없었다**

### 덤으로 드러난 것 — 인자가 애초에 틀렸다

spawn을 고쳐도 gemini·codex는 돌지 않았을 것이다. 두 CLI를 실제로 깔아 확인했다.

- **gemini `-o json`**: 여러 줄로 예쁘게 찍힌 JSON이라 줄 단위 파서가 본문을 한 글자도 못 꺼낸다 → `-o stream-json`
- **codex `--skip-git-repo-check` 누락**: git 저장소 밖에서는 **시작조차 하지 않는다**

6a단계에서 claude만 실측하고 나머지 둘은 문서만 보고 적었던 결과다. 설계 문서에는
"gemini는 Windows에서 실패하면 `cmd /C`로 재시도한다"가 **이미 적혀 있었는데 구현이
그것을 빠뜨렸다** — 문서와 코드가 어긋난 것을 아무도 확인하지 않았다.

### 이번에 바꾼 검증

리눅스에서 증명할 수 없는 것을 리눅스에서만 검증하고 있었다. **Windows job이
`verify:llm`을 돌린다.** 가짜 CLI 셰임을 Windows에서는 `.cmd`로 만들므로, 결함과 똑같은
모양이 CI에서 재현된다. 인자 왕복(`ARGV=`)도 같은 코드로 두 플랫폼에서 돈다.

### 고치지 않은 것

- **두 CLI의 성공 응답 본문.** 인증이 없어 모델을 부를 수 없다. codex는 `--output-last-message` 파일을 안전망으로 걸어 두었다
- **한 인자에 특수문자를 여럿 몰아넣은 경우.** Windows CI에서 `&` `|` `<>` `^` `"` `%` `!` 는 각각 하나씩이면 `.cmd` 셰임 왕복을 견디는 것을 확인했지만, `a&b c"d^e|f` 처럼 섞으면 깨진다. 실제 모델 이름에는 없는 모양이라 막지 않았다 — 방아쇠가 어느 글자인지 확인하지 않은 채 입력을 거절하면 멀쩡한 이름까지 막는다

## build.25 실측 반영 — 배선이 끊긴 두 곳과 틀린 안내 둘

사용자가 [v0.1.0-build.25](https://github.com/yooyoopd-dev/mark-extract/releases/tag/v0.1.0-build.25)
를 사내 Windows PC 에서 돌려 점검표에 답했다. 압축 해제 속도와 스플래시는 문제가
없었고, 나머지 여섯 건이 이번 회차의 일이 됐다.

### 1. OCR·구조 트리 토글이 재변환을 누르면 도로 꺼졌다

> "'OCR 사용' enable 하여 재변환을 누르면 바로 해당 옵션이 disable 되면서 동작 안 함
> ('구조 트리 사용' 역시 다시 disable 됨)"

원인은 어댑터도 렌더러도 아니라 **IPC 경계**였다. `ipc.ts` 의 `cleanOptions()` 가
렌더러에서 온 옵션을 허용 목록으로 거르는데 `ocr` · `hybridFullPages` ·
`useStructTree` 세 키가 목록에 없었다. 7단계 커밋이 타입·렌더러·어댑터·검증을 모두
붙이면서 **이 목록만 빠뜨렸다.**

증상의 시점도 정확히 그 모양이었다. 토글을 켜면 렌더러의 임시값 덕에 켜져 보이고,
재변환이 그 임시값을 버린 직후 돌아온 스냅샷에 키가 없어 화면이 다시 꺼진다.
`retry-with-ocr`("OCR 켜고 재시도") 도 같은 구멍에 빠져 있었다.

### 2. 왜 단언 40개가 통과했나 — 아무도 IPC 를 지나지 않았다

`verify-ocr.mjs` 는 `buildArgsForVerify()` 에 옵션 객체를 **손으로 만들어** 먹인다.
`verify-queue.mjs` 는 `queue.reconvert()` 를 직접 부르고, 마침 고른 두 옵션이
허용 목록에 있는 키였다. 스모크는 "서버가 없을 때 토글이 잠겨 있는지"만 봤다 —
**켜서 재변환까지 돌려 보는 검사가 한 건도 없었다.**

`--quiet` 가 로그를 삼키던 것과 같은 종류다. 층마다 검사가 있었는데 **층 사이**에는
없었다. 이번에 세 자리를 메웠다.

- `verify-queue.mjs` 가 `cleanOptions()` 를 직접 부른다. 세 키가 지나는지, `false` 도
  지나는지(끄는 길), 모르는 키는 여전히 버리는지
- 같은 스크립트가 렌더러가 보내는 모양 그대로 재변환해 **어댑터 명령줄까지** 본다
- 스모크가 인스펙터 토글을 **실제로 눌러** 재변환하고, 토글이 켜진 채로 남는지와
  `--use-struct-tree` 가 인자에 실리는지를 본다

일부러 깨뜨려 확인했다: 허용 목록 한 줄을 지우니 스모크가 세 건을 잡았고, 그중 하나가
사용자가 보고한 문장 그대로였다 — `재변환 뒤에 토글이 도로 꺼졌습니다`.
(컴파일된 `.js` 는 그 한 줄이 두 줄로 갈라져 있다. 8단계 스플래시 때와 같은 함정이라
이번에는 처음부터 두 줄을 지웠다.)

### 3. 설정에 "새 PDF 에 OCR 켜 두기"

스캔 문서가 대부분인 곳에서는 문서마다 토글을 켜는 것이 일이다. `Settings.ocrByDefault`
를 더했다. 기본은 꺼짐이고, **이미 큐에 있는 문서는 건드리지 않는다**(6b 규칙).
주소가 비어 있으면 어댑터가 `--hybrid` 를 붙이지 않으므로 켜 두어도 해가 없다.

### 4. `* ` 로 시작한 줄이 `\* ` 로 나왔다

> "Word 에서 문장 시작에 `* ` 시작하면 Parsing 된 결과에는 `\* ` 으로 출력됨"

우리 코드가 아니었다. kordoc 의 `escapeGfm` 이 `*` `_` `~` `` ` `` 를 **본문 어디에
있든** 이스케이프한다. 어댑터에서 그 역슬래시만 떼어 낸다. 표의 `\|` 는 우리가 파이프
표를 위해 일부러 넣는 것이라 건드리지 않는다.

맞바꿈이 있다 — 원문에 진짜로 `*강조*` 모양이 있으면 이제 뷰어에서 기울임으로 보인다.
원문 글자를 그대로 두는 쪽을 골랐다(사용자 결정).

**PDF 는 애초에 이스케이프하지 않는다**(실측). 같은 자료를 두 엔진에 넣어 확인했다.

시험 자료에 `*` `_` `~` `` ` `` 가 **하나도 없어서** 단언 52개가 다 통과했다.
`sample-table.docx`/`.html` 에 기호로 시작하는 줄을 넣고 두 엔진 모두에서 본다.
build.8 의 "자료에 없는 것은 잡히지 않는다" 가 그대로 되풀이됐다.

### 5. DRM 문서에 엉뚱한 안내를 하고 있었다

> "DRM 이 적용된 문서가 기본이여서 … 프로그램이 DRM 적용 문서를 문서로 아예 인식을
> 못함. DRM 해지하라는 가이드가 필요"

`detect-format.ts` 가 OLE2 컨테이너인데 확장자가 `.xls` 가 아니면 전부 `"unknown"` 을
냈고, 화면에는 **"PDF · DOCX · XLSX · XLS · PPTX 만 변환합니다. HWP 계열은 지원하지
않습니다."** 가 떴다. DRM 얘기가 아니고, HWP 를 꺼내 오해까지 부른다.

- OLE2 안에서 `EncryptedPackage`·`EncryptionInfo` 를 찾거나, 확장자가 OOXML 인데
  ZIP 이 아니면 `"protected"` 로 판별한다. OOXML 은 ZIP 이어야 하므로 그 조합 자체가
  근거다
- 문구를 **"암호 또는 DRM 으로 보호된 문서로 보입니다. DRM 을 해제한 사본으로 다시
  시도해 주세요."** 로 바꿨다. 코드는 `DRM_PROTECTED` — kordoc 이 쓰는 이름과 맞췄다
- **확장자가 바뀌는 경우**가 더 고약하다. 폴더를 훑을 때 확장자만 보고 거르므로
  `.dcm` 같은 이름이면 목록에 들어오지도 않는다. 건너뛴 파일 **이름을 토스트에 적는다**
- 앱이 DRM 을 직접 푸는 것은 하지 않는다 — 솔루션마다 방식이 다르고 확인할 방법이 없다

### 6. 자체 점검이 파일을 남기지 못했다

> "터미널에서 `--self-test --self-test-out …` 입력해도 프로그램 로고창만 나타났다가
> 사라지고 selftest.txt 파일 바탕화면에 생성 안 됨"

`runSelfTest()` 의 파일 쓰기는 **함수 맨 끝**인데 그 앞에 조건 없는 `return 1` 이 둘
있었다(엔진 확인 실패, 시험 자료 없음). 그 경로로 빠지면 파일이 아예 만들어지지
않고, 이유는 `console.log` 로만 나가 단일 exe 에서 유실된다. **가장 알고 싶은 실패일수록
흔적이 남지 않았다.** (그 "로고 창"은 우리 창이 아니라 NSIS 의 `splashImage` 다 —
`--self-test` 는 창을 만들지 않는다.)

- 점검을 도는 부분과 결과를 남기는 부분을 갈랐다. **어디서 끝나든 파일을 쓴다**
- 디렉터리가 없으면 만들고, 그래도 실패하면 `%TEMP%` 의 고정 이름으로 떨어뜨린다
  (바탕 화면이 OneDrive 로 옮겨간 PC 가 있다)
- **앱 안에서 돌릴 수 있게 했다** — 설정 → 일반 → `자체 점검 실행`, 또는 `Ctrl+K` 의
  `자체 점검`. 결과를 다이얼로그에 띄우고 `결과 복사` 를 단다. 사내망 PC 는 로그를
  반출할 수 없으므로 화면의 것을 그대로 가져갈 수 있어야 한다

사용자가 쓴 명령은 PowerShell 이라 `%USERPROFILE%` 가 펼쳐지지 않았을 수도 있다.
어느 쪽이 원인인지는 가리지 못했다 — 릴리스 노트에 cmd 기준 명령과 PowerShell 주의를
함께 적었다.

### 7. 캡션바 정리 (요청)

`파일 · 편집 · 보기 · 도움말`은 마크업만 있고 **클릭 핸들러가 없는 장식**이었다
(네이티브 메뉴도 없다 — `frame: false`). 지우고, 하단 상태바의 톱니를 우측 상단
`설정` 글자 버튼으로 옮겼다. 설정을 여는 길 네 개(버튼·팔레트·`Ctrl+,`·실패 카드)는
모두 `openSettings()` 하나로 모이므로 잃는 경로가 없다.

`design/index.html`(시각적 계약)과 **의도적으로 갈라지는 첫 사례**다. 04 문서의
"타이틀바 주 메뉴" 서술도 같이 고쳤다.

### 아직 남은 것

- **동봉 JRE 를 쓰는가** — 테스트 PC 에 Java 11 이 설치돼 있어 이번에도 가리지 못했다.
  자체 점검의 `Java` 줄이 `동봉 JRE` 인지 보면 된다
- LLM 4종(gemini·codex 본문, 모드 A 매트릭스, Ollama 실동작) — 사용자가 따로 시험한다
- 실제 OCR 인식 품질 — 서버를 띄운 뒤에야 볼 수 있다

## build.27 — zip 배포로 바꿨다

사용자 요청이다. "실행할 때마다 푸는 exe 말고, zip 으로 받아 한 번 풀고 바로 쓰자."

`portable` 타깃은 매번 660MB 를 `%TEMP%` 에 풀고 끝나면 지웠다. 캐시가 불가능하다는
것은 `portable.nsi` 를 읽어 확인했고(`RMDir /r` 가 앞뒤로 있다), `useZip` 으로 2회차를
17.5~21.4초에서 12.7~12.8초까지 줄였지만 **여전히 매번 풀었다.** 푸는 일을 사용자가
한 번만 하게 하면 그 구간은 통째로 사라진다.

| | build.26 까지 | build.27 부터 |
|---|---|---|
| 배포물 | 자기 압축 해제 exe 1개 | 폴더를 만 zip 1개 |
| 실행 전 | 매번 660MB 압축 해제 (10~26초) | **없음** (푸는 것은 처음 한 번) |
| 로고 창 | NSIS 비트맵 + BrowserWindow 두 겹 | BrowserWindow 한 겹 |

**정한 것**

- `electron-builder` 는 `dir` 로만 만들고 **CI 가 zip 을 만다.** 내장 `zip` 타깃은
  최상위 폴더 없이 말아, 바탕 화면에 바로 푸는 사람이 파일 수백 개를 뒤집어쓴다
- 로고 창은 **문구만 고쳐 유지한다.** 압축 해제는 없어졌지만 Electron 이 뜨는 1~2초는
  남고, 사내 PC 는 백신 검사가 겹친다. 아무것도 안 뜨면 두 번 누르는 사람이 생긴다
- **portable exe 는 더 내지 않는다.** 한 회차 동안 둘 다 내는 쪽은 쓰는 법이 갈려
  혼란만 키운다

**CI 점검을 사용자가 하는 순서로 바꿨다.** 전에는 `dist/*.exe` 를 그냥 돌렸는데, 이제는
**zip 을 실제로 풀고** 그 안의 exe 를 JDK 없는 PATH 로 돌린다. 푸는 과정에서 무엇이
빠지거나 깨지는 것까지 이 단계가 잡는다. 푼 결과가 폴더 하나로 감싸여 있는지,
`resources/jre/bin/java.exe` 와 JAR 이 그 안에 있는지도 함께 본다.

`out/verify/portable-timing.txt` 는 `startup-timing.txt` 가 됐다 — 같은 두 번 실행이지만
이제 재는 것이 압축 해제가 아니라 **앱이 뜨는 시간**이다.

**따라 없어진 것 셋** — `portable.splashImage`(와 `build/splash.bmp`), `portable.useZip`,
그리고 **stdout 이 호출자에게 닿지 않던 문제**. 셋 다 NSIS 스텁이 있어서 생긴 것이었다.
`--self-test-out` 은 그대로 둔다(사용자 안내가 그것을 쓴다).

8단계에서 압축 해제 시간을 재며 쌓은 기록은 [05](05-packaging.md#첫-실행) 에 지우지 않고
남겼다 — 같은 선택을 다시 검토할 사람이 읽을 것이다.
